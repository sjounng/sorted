# Sorted 기획안

Sep 27, 2026 · @June

## 개요

Sorted는 LMS에서 받은 강의자료를 사용자가 아무것도 하지 않아도 과목별로 정리하고, 중복을 막고, 새 버전이 오면 바뀐 부분을 짚어주는 도구다. 크롬 확장은 다운로드 순간의 출처 정보만 넘기고, 메뉴 막대에 상주하는 맥 앱이 판정·정리·비교를 맡는다.

- 대상: LMS에서 강의자료를 받는 학생
- 핵심 원칙: 설치 후 사용자의 추가 행동 0회
- 과목 맥락: CSE406 소프트웨어공학 Phase 1 (스크래치 프로젝트, 중간고사 대체, 교수님과 3분 1:1 시연)
- 규모와 역할: 약 열흘, 예원(프론트엔드)·준우(백엔드)

## 문제

강의자료는 다운로드 폴더에 흩어지고, 같은 파일이 여러 번 쌓이고, 새 버전은 예고 없이 같은 자리에 교체된다.

- 흩어짐: 과목 구분 없이 다운로드 폴더에 섞인다.
- 중복: 같은 자료를 다시 받으면 `이름 (1).pdf`가 쌓인다.
- 조용한 교체: 한양대 LMS의 다운로드 주소는 `content_id`와 고정 경로(`original.pdf`)로 이뤄져 있어, 파일이 교체돼도 주소가 같을 가능성이 높다(미검증).
- 가장 아픈 경우: 과제 명세가 바뀐 걸 모르고 제출하는 일.

기존 도구로는 [Acrobat 비교](https://helpx.adobe.com/acrobat/using/compare-documents.html)나 [Compare PDF Tool](https://chromewebstore.google.com/detail/compare-pdf-tool/cobkffhdclimlamjmdkchlcemhbpppka)처럼 PDF 두 개를 직접 골라 비교하는 것이 있다. 다운로드를 자동으로 감지해 이전 버전과 비교하는 도구는 찾지 못했다. 차별점은 사용자가 아무것도 안 해도 된다는 점이다.

## 핵심 기능

과목별 정리, 중복 방지, 변경 비교 순서로 만든다. 앞의 둘은 해시와 메타데이터만 다뤄 가볍고, 변경 비교는 PDF 파싱과 슬라이드 정렬이 필요해 가장 무겁다.

| 우선순위 | 기능                     | 사용자가 보는 것                                                                                                  | 담당         |
| -------- | ------------------------ | ----------------------------------------------------------------------------------------------------------------- | ------------ |
| 1        | 과목별 자동 정리         | 받는 순간 `과목명/주차/원래파일명.pdf`로 옮겨짐 (\~/Sorted)                                                       | 확장 + 맥 앱 |
| 2        | 중복 다운로드 방지       | 받은 직후 “이미 받은 파일이에요 \[기존 파일 열기\] \[둘 다 보관\]”                                                | 맥 앱        |
| 3        | 새 버전 변경 비교        | “v2 대비 3장 변경” 알림 → 앱 창에서 새 버전 슬라이드에 바뀐 부분 강조, 사이드바 변경 목록을 누르면 그 장으로 이동 | 맥 앱        |
| 3        | 구버전 정리              | “이전 버전을 지울까요?” 필기가 있으면 경고, 지우면 비교용 데이터도 삭제                                           | 맥 앱        |
| 4        | 파일에 메타데이터 새기기 | 파일을 옮기거나 이름을 바꿔도 과목을 기억                                                                         | 맥 앱        |
| 스트레치 | 기존 파일 가져오기       | 설치 전에 받은 자료도 정리                                                                                        | 맥 앱        |
| 스트레치 | LMS 페이지 표시          | “안 받은 자료 2개, 새 버전 1개”                                                                                   | 확장         |

시간이 모자라면 변경 비교는 “바뀐 페이지 번호만 표시”하는 최소 버전으로 자른다.

## 사용자 흐름

사용자가 하는 일은 설치와 첫 설정 한 번뿐이고, 그다음부터는 평소처럼 LMS에서 받기만 한다.

1. 확장과 맥 앱을 설치하고, 첫 실행 때 정리 폴더 위치와 다운로드 폴더 접근을 허락한다.
2. LMS에서 평소처럼 PDF를 받는다.
3. 확장이 출처 정보를 앱에 넘기고, 다운로드가 끝나면 앱이 파일을 판정해 네 갈래로 나뉜다.
   - 처음 보는 문서: `~/Sorted/<과목명>/<주차>/`로 옮긴다. 알림 없음.
   - 과목을 모르는 문서: 과목을 한 번 묻고 기억한 뒤 옮긴다.
   - 같은 문서, 같은 내용: “이미 받은 파일이에요”를 띄우고, \[기존 파일 열기\]를 고르면 방금 받은 복사본을 휴지통으로 보낸다.
   - 같은 문서, 다른 내용: `(v2)`를 붙여 새 버전으로 옮기고 “v2 대비 N장 변경” 알림을 띄운다.
4. 알림을 누르면 앱 창에서 새 버전 슬라이드의 바뀐 부분이 강조되고, 사이드바의 변경 목록을 누르면 그 장으로 이동한다.
5. 이어서 구버전을 지울지 묻고, 필기가 있으면 경고한다.

## 아키텍처

크롬 확장이 웹을, 맥 앱이 디스크를 맡고, 둘은 네이티브 메시징으로만 대화한다. 각자 자기 일에 필요한 권한만 갖는 최소 권한 구조다.

> 그림 "아키텍처 · 확장과 맥 앱, 네이티브 메시징"은 원본 기획안에서 볼 수 있다 (마크다운으로 내보낼 수 없음).

판정 코어는 맥 앱(Rust) 안에 있다. 확장은 출처 정보만 넘기고, 앱이 받은 파일을 직접 읽어 판정·정리·비교를 하고 과목 ID와 `content_id`를 파일 속성에 새긴다.

- 도메인 모델: 과목(Course) → 문서(Document) → 버전(Version: 해시·크기·받은 시각) → 페이지(Page: 텍스트·이미지 지문)
- 연결 방식은 네이티브 메시징 + 유닉스 소켓: Chrome은 메시지마다 중계 프로그램을 새로 띄우므로, 중계 프로그램이 메뉴 막대 앱의 유닉스 소켓(본인만 접근)으로 넘긴다. 허락한 확장 ID만 중계 프로그램을 부를 수 있고, `localhost` 서버처럼 포트를 열지 않는다. 앱이 꺼져 있으면 중계 프로그램이 보관했다가 앱이 켜질 때 넘긴다 (#1에서 확인).
- 입력은 어댑터로 분리한다. 지금은 한양대 LMS 어댑터 하나만 구현하고, 다른 LMS는 같은 인터페이스 뒤에 붙인다. 한양대 어댑터는 다운로드 정보에 더해 LMS(Canvas) API로 과목명과 주차(모듈)를 조회한다.
- 앱은 필수다. 정리 폴더를 다운로드 폴더 밖에 두기로 해서, 파일 이동과 관리를 Tauri(Rust + TypeScript)로 만든 앱이 맡는다.
- 재수집 없음: 앱이 다운로드된 파일을 직접 읽으므로 확장은 LMS에 파일을 다시 요청하지 않는다. 중복은 다운로드가 끝난 뒤 판정한다.
- 앱은 메뉴 막대에 상주하고, 변경 비교 화면도 앱 창에서 연다.
- 판정 보조 서버(선택): 규칙으로 가르기 어려운 경우만 클라우드에 묻는다. 지금은 "이름과 content\_id가 다른데 같은 강의의 새 버전인가"(FR-18) 하나다. 앱은 중계 서버(Lambda)를 부르고, 서버가 LLM을 호출해 판정과 확신도를 돌려준다. API 키는 서버에만 둔다.

## 판정 규칙

모든 기능은 “이 파일은 어느 과목, 어떤 문서의 몇 번째 버전인가”라는 한 질문에 기댄다. 스파이크 결과로 규칙을 이렇게 잡았다.

- 문서 식별: 다운로드 URL의 `content_id`(예: `6aa284ef1cf74`). 다시 받아도 같은 값이다. 없으면 LMS 모듈 항목 번호, 그것도 없으면 파일명에서 `v2`·`final`·`수정`을 지운 이름으로 추정한다.
- 버전 판정: 앱이 받은 파일 전체의 SHA-256을 계산한다. 파일을 다시 받지 않으므로 서버 메타데이터는 쓰지 않는다.
- 과목 판정, 앞에서부터 순서대로 시도한다.
  1. referrer 안의 `courses/<ID>` (예: `210208`)
  2. 다운로드 순간 활성 탭 주소의 `courses/<ID>` (#3에서 확인)
  3. 파일명의 과목 코드 (예: `cse406`)
  4. 첫 페이지 텍스트
- PDF 판정: 서버가 MIME을 `application/octet-stream`으로 보내므로 믿지 않는다. 확장자와 파일 앞 5바이트 `%PDF-`로 판정한다.
- 폴더 구조: `~/Sorted/<과목명>/<주차>/<원래 파일명>.pdf`. 순서는 파일명이 아니라 LMS 모듈(주차)과 그 안의 순서에서 가져오고(Canvas API, #3에서 확인), 못 읽으면 게시일 순이다. 원래 파일명은 바꾸지 않고 새 버전만 끝에 `(v2)`를 붙이며, 사용자가 순서를 고치면 그 과목에만 기억한다.
- 과목명·주차: 확장이 과목 ID로 LMS(Canvas) API에 물어 과목명(`202620HY11171_소프트웨어공학` → `소프트웨어공학`)과 주차(모듈)를 받는다. 주차는 자료 뷰어 주소의 모듈 항목 번호로, 없으면 항목 제목 = 파일 이름으로 짝짓는다. 다운로드 순간의 탭 제목은 파일 이름이라 쓰지 않는다 (#3). 조회가 안 되면 처음 한 번만 사용자에게 묻고 기억한다.
- 새 버전 찾기: content\_id·모듈 항목 번호·이름이 모두 다르면 별개 문서로 본다. 다만 같은 과목에 이름이 비슷한 문서가 있으면 판정 보조 서버에 물어, 확신도가 높을 때만 새 버전으로 묶는다 (FR-18).
- 모듈 이름의 주차: 교수님마다 모듈 이름이 다르므로(`1주차/Unit-1`, `[Week01]`) 이름에서 주차 숫자를 읽어 `N주차`로 맞춘다. 숫자가 없으면 모듈 이름 그대로다 (FR-17). 공지·과제 게시일로 계산하는 방식은 첨부 기능이 없는 과목이 있어 접었다.

## 기술 검토 기록

맥 앱 단독안이 더 나아 보여 먼저 검증했고, 크롬이 파일에 출처를 남기지 않는다는 걸 대조 실험으로 확인해 확장을 중심에 두었다. 명령어와 출력은 레포 이슈에 그대로 남긴다.

## 비기능 요구사항과 개인정보

모든 처리는 사용자 컴퓨터 안에서 끝나고, 강의자료와 학번은 밖으로 나가지 않는다.

- 지원 환경: 데스크큱 크롬과 macOS만 지원한다. 윈도우와 다른 브라우저는 범위 밖이다.
- 정리 폴더: 홈 바로 아래 `~/Sorted`에 둔다. Finder에서 보이고, 보호 폴더(문서·데스크톱)가 아니라 권한 창이 다운로드 폴더 하나로 줄고, iCloud 동기화로 파일이 클라우드에만 남는 문제도 피한다. 위치는 설정에서 바꿀 수 있다.
- 삭제: 파일은 항상 휴지통으로 보내 되살릴 수 있게 한다.
- 로컬 처리: 정리와 판정은 모두 맥에서 한다. 서버는 판정 보조 하나뿐이고, 꺼도 동작한다. 판정 보조 서버에는 파일명·첫 페이지 글자·비교할 후보 문서 이름만 보내고(PDF 파일·학번·URL은 보내지 않음), 처음 쓸 때 사용자 동의를 받는다. 애매한 경우에만 부르므로 호출은 드물다.
- 학번: referrer의 `user_id`는 저장하지 않고, 로그와 레포 이슈에서도 지운다.
- 파일에 새기는 속성: 과목 ID와 `content_id`만. URL 전체는 넣지 않는다.
- 몰래 취소 금지: 중복이면 다운로드를 멈추고 사용자에게 묻는다.
- 추가 요청 없음: 파일을 다시 받지 않아 LMS에 추가 트래픽을 만들지 않는다.
- 권한 최소화: 스파이크는 모든 사이트 권한이었지만, 본 확장은 한양대 LMS 도메인만 요청하고, 앱은 다운로드 폴더와 정리 폴더에만 접근한다.
- 이전 버전 파일: 새 버전이 오면 지울지 사용자에게 묻고, 동의하면 지운다. 구버전에 필기가 있으면(받을 때의 해시와 달라졌으면) 경고하고, 지울 때 파일은 휴지통으로 보내고, 비교용 페이지 이미지와 지문은 바로 지운다.

## 오류 처리

판정이 확실하지 않으면 아무것도 건드리지 않고 다운로드 폴더에 그대로 둔 채 알린다. 파일을 잘못 옮기거나 지우는 것보다 정리가 안 되는 편이 낫다. 처리하지 못한 파일은 메뉴 막대에 목록으로 모은다.

| 상황                                              | 처리                                                                         |
| ------------------------------------------------- | ---------------------------------------------------------------------------- |
| LMS 로그인 만료로 PDF 대신 로그인 페이지가 저장됨 | `%PDF-` 검사에서 걸러 “LMS 로그인이 만료된 것 같아요”라고 알리고 파일을 둔다 |
| 앱이 꺼져 있거나 확장과 연결 실패                 | 확장이 출처 정보를 보관했다가 연결되면 넘긴다. 파일은 다운로드 폴더에 그대로 |
| 다운로드 중단·취소                                | 완료된 다운로드만 처리한다                                                   |
| 과목을 못 알아냄                                  | 한 번 묻는다. 무시하면 다운로드 폴더에 두고 목록에 남긴다                    |
| 주차를 못 알아냄                                  | 게시일 순, 그것도 없으면 과목 폴더의 `미분류`로                              |
| 다운로드 폴더 권한 거부                           | 메뉴 막대에 경고와 \[설정 열기\] 버튼                                        |
| 정리 폴더에 같은 이름 파일이 있음                 | 덮어쓰지 않고 이름 뒤에 번호를 붙인다                                        |
| 이동 실패(디스크 공간 등)                         | 원래 자리에 두고 나중에 다시 시도한다                                        |
| 암호가 걸렻거나 손상된 PDF                        | 정리는 하되 “비교할 수 없는 파일”로 표시한다                                 |
| 처리 중 앱이 꺼짐                                 | 작업 상태를 저장해두고 다시 켜지면 이어서 한다                               |

오프라인은 문제가 아니다. 파일을 다시 받지 않으므로 다운로드 뒤로는 네트워크가 필요 없다.

## 평가 계획

정답을 미리 알 수 있게 만들어서 기능별로 잔다.

- 변경 비교: 실제 강의자료를 프로그램으로 편집해(삽입·삭제·수정·순서 변경·한 장을 둘로 분할) 정답이 있는 버전 쌍을 만든다. 편집 종류별 정밀도와 재현율을 본다.
- 과목 판정: 실제 다운로드에서 referrer, 활성 탭, 파일명, 내용 신호가 각각 몇 % 성공하는지 잔다. 표본 수는 같이 정한다.
- 중복 판정: 같은 파일 재다운로드, 같은 URL의 새 파일, 다른 URL의 같은 파일 세 경우에서 오판 수를 연다.
- 사용자 수고: 설치 후 추가 행동이 0회인지 확인하고, 수동 PDF 비교 도구와 단계 수를 비교한다.

## 개발 프로세스

GitHub Flow로 일하고, 모든 작업은 이슈에서 시작해 상대 1명의 승인을 받은 PR로만 main에 들어간다. 교수님이 보겠다고 한 git·이슈 히스토리·코드 리뷰가 이 규칙에서 그대로 남는다.

| 영역                                                                                                                           | 담당 |
| ------------------------------------------------------------------------------------------------------------------------------ | ---- |
| 앱 화면: 메뉴 막대(과목 목록·최근 변경·처리 못한 파일), 첫 실행 설정, 중복 안내, 과목 지정, 비교 창과 사이드바, 구버전 정리 창 | 예원 |
| 확장: 다운로드 감지, 출처 정보 수집과 보관                                                                                     | 준우 |
| 앱 내부(Rust): 네이티브 호스트, 판정 코어, 파일 이동·휴지통·속성 기록, 파일 추적, 슬라이드 정렬, 필기 감지                     | 준우 |

- 저장소: 하나의 레포에 `extension/`(크롬 확장), `app/`(Tauri, 판정 코어 포함), `spike/`(스파이크 코드 보존), `docs/`를 둔다.
- 브랜치: main은 항상 돌아가는 상태. 작업은 `feat/<이슈번호>-<이름>`, `fix/…`, `spike/…` 브랜치에서 한다.
- 이슈: 기능 요구사항(FR) 하나 또는 스파이크 하나당 이슈 하나. 라벨은 `feature`·`bug`·`spike`·`docs`, 보드는 GitHub Projects의 할 일·진행 중·완료. 스파이크 이슈에는 명령어와 출력을 그대로 남긴다.
- 커밋: 한 커밋에 한 변경, 메시지에 이슈 번호(`#12`)를 넣는다.
- PR: 본문에 `Closes #12`와 관련 FR 번호, 화면이 바뀌면 스크린샷. 상대 1명 승인 후 머지한다.
- 요구사항 추적: 이슈 제목에 FR 번호를 붙이고, PR 본문에 그 FR의 인수 조건을 체크리스트로 넣어 리뷰어가 확인한다. 이슈·PR 템플릿으로 고정한다.
- CI: GitHub Actions가 PR마다 포매터·린트·타입 검사·단위 테스트를 돌린다. TypeScript는 Prettier·ESLint·tsc·Vitest, Rust는 rustfmt·clippy·cargo test.
- 테스트 데이터: 합성 PDF 버전 쌍은 `fixtures/`에 커밋하고, 실제 강의자료와 학번이 들어간 로그는 `.gitignore`로 막는다.

## 범위와 일정

날짜는 고정하지 않고 단계별로 진행한다. 각 단계는 ‘끝났다는 기준’을 통과해야 다음으로 넘어가고, 발표일이 정해지면 거꾸로 맞춘다. 시연은 2·3단계 기능만 쓰므로, 시간이 모자라면 4단계의 변경 강조를 ‘바뀐 페이지 번호만’으로 줄인다.

| 단계           | 예원                                         | 준우                                                                                             | 끝났다는 기준                                                                           |
| -------------- | -------------------------------------------- | ------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------- |
| 1. 기반        | 레포·CI·이슈 템플릿 세팅, 메뉴 막대 앱 뼈대  | 2차 스파이크: 활성 탭 과목 ID, 해시, 주차·과목명 읽기, 다운로드 폴더 권한, Tauri 네이티브 메시징 | 검증할 가정이 모두 확인되거나 대안이 정해짐                                             |
| 2. 정리        | 첫 실행 설정, 과목 지정 창                   | 확장의 다운로드 감지, 판정 코어, 파일 이동과 속성 기록, 모듈 이름별 주차 맞추기                  | 실제 LMS에서 받은 파일이 `~/Sorted`의 과목·주차 폴더로 옮겨짐 (FR-1\~6, 11\~12, 15, 17) |

| 5. 마무리      | 화면 다듬기, 시연 리허설                     | 평가 집계, 설계 문서 영어 번역                                                                   | 3분 시연이 실제 LMS에서 끝까지 돎                                                       |

## 3분 시연

슬라이드 없이 노트북으로 한다. 실제 LMS에서 시연한다.

1. 문제: “Have you ever submitted an assignment without knowing the spec had quietly changed?”
2. 시연: 실제 LMS에서 받기 → 과목 폴더에 저장 → 다시 받기 → 중복 안내 (새 버전과 변경 비교는 시연하지 않고 설계로만 설명)
3. 설계: 아키텍처 그림, 그리고 맥 앱 단독안을 검증한 뒤 확장과 앱으로 나눈 과정 한 문장
4. 숫자 하나와 git log·이슈 히스토리를 보여주고 닫기

## 리스크

가장 큰 리스크였던 LMS 재수집은 스파이크로 풀렸고, 남은 건 대부분 판정 신호의 신뢰도다.

| 리스크                                         | 대응                                                        |
| ---------------------------------------------- | ----------------------------------------------------------- |
| 파일이 교체돼도 `content_id`가 유지되는지 모름 | 학기 중 재업로드 사례 관찰, 못 하면 파일명 기반 식별로 폴백 |
| 활성 탭에 과목 ID가 없을 수 있음               | 파일명·내용 폴백, 판정 불가 시 사용자에게 한 번 물어 기억   |
| LMS 구조가 바뀔 수 있음                        | 한양대 LMS 어댑터를 분리해 고칠 곳을 한 곳으로              |
| 그림 위주 슬라이드는 텍스트 비교 불가          | 페이지 이미지 지문(pHash) 병행                              |
| 열흘 범위 초과                                 | 변경 비교는 “바뀐 페이지 번호만”으로 축소                   |

## 같이 정할 것

아래는 아직 정하지 않았거나 검증하지 않은 것들이다. 정해지면 체크하고 위 절에 반영한다.

결정 사항

- [x] 제품 이름
- [x] 페어 파트너와 역할 분담 (파트너가 맥을 쓰는지 포함)
- [x] 정리 폴더 위치: 별도 폴더로 결정, 맥 앱이 파일을 관리한다
- [x] 폴더·파일 이름 규칙, 과목 ID를 과목명으로 바꾸는 방법
- [x] 중복일 때 기본 동작: 매번 묻기 vs 기존 파일 바로 열기
- [x] 변경 비교 범위: 바뀐 페이지 번호만 vs 슬라이드 정렬과 나란히 보기
- [x] 이전 버전의 원본 보관 여부
- [x] 지원 형식: PDF만 vs PPTX도
- [x] 맥 앱 기술: Tauri로 할지 (정리 폴더를 앱이 관리하므로 범위에는 넣기로 함)
- [x] 제출 문서 언어: 과제는 영어로 작성해야 함(강의 0 슬라이드 34)
- [x] 필기 처리: 구버전은 덮어쓰지 않고 지울 때 감지·경고까지만 (필기 옮기기는 하지 않음)
- [x] 정리 폴더: \~/Sorted(홈 바로 아래, Finder에서 보임), 삭제는 휴지통으로 결정
- [x] 오류 처리: ‘확실하지 않으면 손대지 않기’로 결정 (오류 처리 절)
- [x] 지원 환경: 크롬·맥 전용으로 결정
- [x] 시간이 모자랄 때 변경 비교를 “바뀐 페이지 번호만”으로 줄이는 대안은 남겨두기로 결정
- [x] 팀 인원: 준우·제니 2명
- [x] 파일 추적: \~/Sorted 안에서 옮기거나 이름을 바꾼 파일도 앱이 따라가기로 결정 (메타데이터 새기기를 필수로, FR-14)

검증할 가정

- [x] 활성 탭 주소에서 과목 ID가 잡히는가 (2차 스파이크)
- [x] 같은 파일을 두 번 받으면 해시가 같은가
- [x] 앱이 다운로드 폴더의 파일을 읽을 수 있는가 (macOS 권한, 빌드한 앱에서 권한 창 확인)
- [ ] 교수님이 파일을 교체해도 `content_id`가 유지되는가 (다시 받기로는 같음을 확인. 교체는 관찰 필요, 바뀌면 모듈 항목 번호로 묶는다)
- [x] 주차·과목명을 LMS에서 읽을 수 있는가 (Canvas API로 가능)
- [x] Tauri 네이티브 호스트가 크롬 확장과 통신되는가
